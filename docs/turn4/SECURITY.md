# T4 security and limits

Trust roots, policy, time, current snapshot, allowed reads, code handlers, native dependency pins and
filesystem custody remain host responsibilities. An agent's work order contains explicit scope, not a
universal capability. Data posing as instructions stays inert text in the fixed handlers and GUI.
This is not a claim that arbitrary model/agent prompting is immune to prompt injection.

Rehashing a modified work order or PASS report cannot replace exact replay against the accepted pins.
Recognized negative evidence is retained. Observer identity authentication establishes who signed,
not physical truth or exhaustive source coverage. Legacy fallback after a newer expired negative
observation remains refused by the unchanged T3 evaluator.

Core T1/T2/T3 bytes are preserved. T4 introduces new hashes and schemas rather than silently changing
accepted outputs. SDK source hashes identify the selected function's file; they do not recursively
attest every import/global nor constrain trusted handler effects. Callers should review and isolate
extensions proportional to their risk. Only fixed built-ins are reachable through the untrusted ABI.

Operational and GUI tests run on one Linux host. Windows/WSL/macOS, actual production HTTPS, distributed
custody, real adapter approval, production recognition, native P/PPI/UCM admission and independent review
are not established. Unit tests, simulated confirmations and unsigned qualification receipts do not
substitute for those gates. Full T5 end-to-end and comparative productivity requirements remain open.
